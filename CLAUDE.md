## Project status and purpose

`true-fit` is a hackathon project for the **Junction "Rethinking Recruitment" challenge by the City of Espoo**. The brief is in `espoo-challenge.pdf` at the repo root. It is untracked; on macOS, extract its text with PDFKit via `osascript -l JavaScript` if `pdftotext` isn't installed.

The MVP UI is a **front-end demo with a few API routes for the LLM steps**, all using **Google Gemini** through `@google/genai` (`lib/ai.ts`, default model `gemini-3.5-flash-lite`, override with `GEMINI_MODEL`; key in `GEMINI_API_KEY`). `app/api/intake` runs the company intake chat (its suggested answers are written by Gemini in the user's voice and tailored to the conversation, then cleaned by `cleanQuickReplies`; whenever the reply asks about the working language and the card has none, they are fixed to Finnish / Swedish / English / Another language by `withLanguageReplies`), `app/api/intake/starters` writes the opening suggestions from aggregate pool counts (cached hourly, fixed fallback); `app/api/intake/transcribe` turns a mic recording from the chat (up to 60 s, `components/voice-input.tsx`) into text with Gemini (`transcribeAudio` in `lib/ai.ts`); the transcript fills the chat box for the user to check, it is never sent automatically, and the audio is not stored; `app/api/intake/live` starts a **live voice conversation** (Gemini Live API, model `gemini-3.8-live`, override with `GEMINI_LIVE_MODEL`): it returns a single-use ephemeral token with the model, system prompt (card + aggregate pool counts) and the `update_need_card` tool locked in, so the key never reaches the browser; `components/use-live-intake.ts` streams 16 kHz mic PCM, plays 24 kHz replies, shows both transcripts in the chat and answers each tool call with `cardPoolCheck` counts only (`lib/intake-live.ts`); `app/api/match/rank` gives an optional **AI fit rate** (0–100 plus a one-line reason) for already-matched candidates: Gemini sees only the scoring output and evidence quotes under labels C1…Cn, never ids or names, the output is re-validated (`lib/match-rank.ts`, rules fallback), and the UI (`components/ai-rank.tsx`, "Order by: Skill match / AI fit rate" on Find candidates and Candidates) keeps the skill match beside it and never hides anyone; `app/api/talent/translate` (job title or career path → ESCO skills + Finnish job-ad vocabulary) `app/api/talent/starters` (writing ideas and half-sentence starters tailored to the person's skills and background, never full answers) `app/api/talent/evidence` (answers → ESCO skills with verbatim supporting quotes, plus a privacy check) and `app/api/talent/cv` (CV import: LinkedIn "Save to PDF" export or any ATS-style CV: text-based PDF via `unpdf`, Word .docx via `fflate`, plain or pasted text; basic mode knows common English/Finnish/Swedish CV headings and date formats → latest title, anonymised career summary, quote-backed skills and languages; contact details are stripped before Gemini, the file is never stored, logic and rules fallback in `lib/cv-import.ts`, UI in `components/cv-import.tsx`) power the talent card. Skills from a CV only ever count as _stated_; the scenario answers are what can show them. On the need card, working language, way of working and contract type are **free text** (presets are one-tap shortcuts) and Gemini may set or change any card field to any wording; only skills stay limited to the cached ESCO ids. `lib/need-terms.ts` reads that text back for pool counts, the native-speaker warning and the online-room check; seed needs still use the presets (the `db/schema.sql` CHECKs only cover seeds). The intake's quick replies and their hints ("6 in the pool", "+2 relevant") come from aggregate pool counts in `lib/intake.ts`; Gemini gets only those counts, never individuals. Each Gemini call is capped at 15 s, and after an overload or timeout the routes skip Gemini for 60 s. Responses use JSON-schema output constrained to the cached ESCO ids and are re-validated server-side (quotes must appear verbatim in the answer). **The company intake chat requires Gemini and an internet connection, with no fallback**: without a key or on an API error `app/api/intake` returns `{ error }` (503/502) and the chat shows the error with a retry; offline, input is disabled (the need card stays editable by hand). The intake rules engine (`rulesTurn` in `lib/intake.ts`) is no longer wired to the chat; its pool-aware helpers still drive the quick-reply hints. The talent and match-explanation routes keep their deterministic fallbacks (`lib/talent-ai.ts`, `lib/match-explain.ts`): without a key, on any API error, or with `AI_MODE=rules`, they answer from rules. Routes only see the sender's own text, never other people's data. All data is synthetic. Demo state lives in a client context (`lib/store.tsx`) and is **saved to the database**: `app/api/demo-state` (GET / PATCH / DELETE for reset) reads and writes the tables `pipeline_pairs` (one row per need × candidate: decision, opt-ins, Espoo interview, company interview slot, offer, feedback), `pipeline_audit`, `demo_cards` (cards created in the demo) and `demo_state_meta` (version counter). The browser sends per-pair patches (`diffSnapshot`, validated server-side by `cleanPatch` in `lib/demo-state.ts`; queries in `lib/demo-state-db.ts`), compares rows with key-order-independent `stableJson` (jsonb reorders keys), polls every 4 s so other browsers see changes, and shows Saved / Not saved in the header. `localStorage` is only a first-paint cache; `actingAs` stays per browser.

**Mock sign-in and RBAC** (`lib/auth/`): `/login` lets you sign in as a demo account (the Espoo event team, a seed company or a seed candidate), no passwords. Companies create their own account the same way (`signUpCompany`, table `company_accounts`, id `C-<10 chars>`); seed companies and their roles are **view-only** (`needCardProblem` in `lib/auth/patch-rbac.ts`; `components/my-company.tsx` shows their roles with suitable candidates and introduction requests), a company may only save role cards carrying its own id and name, and the Espoo account can't edit any company's or candidate's information. There is no shared `C-YOU` login. Job seekers create their own account with name + email (`signUpJobSeeker`, table `job_seeker_accounts`, `lib/auth/job-seekers.ts`: unique id `T-<10 chars>`, same email signs back in, capped at 2000, per-IP throttle), so a crowd never shares or overwrites a profile; there is no shared `T-YOU` login any more. Seed candidates' profiles are **view-only** (server-enforced in `authorizePatch` and `PUT /api/talent/profile`; `components/my-profile.tsx` shows them read-only) but they can still apply and go through the pipeline. A demo reset clears the pipeline and need cards but keeps job seekers' accounts, cards and saved profiles; an empty pipeline is seeded via `bootstrapPatch`, which drops other people's cards. The session is an HMAC-signed httpOnly cookie `tf_session` (`lib/auth/session.ts`, Web Crypto, secret `AUTH_SECRET` with a demo fallback, 12 h); server actions in `lib/auth/actions.ts` (`signIn`, `signOut`, `switchAccount` for the demo "sign in as the candidate" shortcuts). `lib/auth/rbac.ts` holds the permissions per role and the page/API rules; `proxy.ts` enforces them (signed out → `/login?next=`, wrong role → `/login?role=…&denied=1`, API → 401/403) and every route handler checks again with `requireAccess` (`lib/auth/server.ts`). `PATCH /api/demo-state` is checked field by field against the database by `authorizePatch` (`lib/auth/patch-rbac.ts`): decisions, Espoo results and the log are organiser-only, each side writes only its own answers on its own pairs, a company saves only its own need cards and a candidate only their own card; only the organiser may reset (an empty database is seeded by any signed-in browser). The signed-in account is the identity on each side (`useIdentity`), the header shows only that role's tab, and `/` is a public job-portal landing page (`components/job-board-home.tsx`); `/talent/explore` ("Find jobs") is a job board with search, filters and "Apply now". A job seeker's profile builder autosaves to `candidate_profiles` (one row per signed-in candidate, `app/api/talent/profile`, validated by `cleanDraft` in `lib/candidate-profile.ts`, emptied by a demo reset).

**All data lives in the database; the repo holds no data files.** **Tiger Data** (Timescale Cloud, `TIGER_DATABASE_URL`, password in `TIGER_DATABASE_PASSWORD`, which replaces any password in the URL) is the preferred database: when set, `dbConfig()` in `lib/db-config.mjs` picks it over Supabase for the app and every `yarn db:*` script (TLS verified against Node's public CA store, `sslmode` dropped; `TIGER_DATABASE_CA` pins a CA). The database is the source of truth: `yarn db:migrate` only creates or upgrades the tables from `db/schema.sql` and never touches their contents; `yarn db:dump [dir]` snapshots the ESCO subset and seeds to JSON (`db/snapshot/`, gitignored); `yarn db:migrate --from <dir>` loads a snapshot back (replacing those tables, `--talent-only` for just the candidates); `yarn db:migrate --scraped` loads `data/scraped` (the `yarn scrape` output) into `scraped_sources`/`scraped_items`; `yarn db:sql --from <dir>` / `yarn db:csv --from <dir>` write the same load as SQL or CSV. `lib/db-read.mjs` (`readEsco`, `readSeed`) turns the tables back into the snapshot shape, shared by the app and the dump. The server reads everything through `lib/seed-db.ts`: `getEsco()` and `getSeed()` (`"use cache"`, seeds validated by `loadSeed`) also fill the in-memory registries in `lib/esco.ts` (`setEsco`) and `lib/seed.ts` (`setSeed`), whose exported arrays/maps (`SKILLS`, `SKILL_BY_ID`, `SEED_TALENT`, `COMPANIES`, …) are filled in place, so every API route that touches ESCO or seed helpers starts with `await getEsco()` / `await getSeed()`. The root layout passes both to `DemoProvider`, which fills the browser's registries before its children render. Never read registry data at module top level (build prompts, schemas and lookups lazily inside functions). **There is no fallback**: without a reachable database pages and routes error. **The database is read at request time only, never in the build pipeline**: `getSeed()`/`getEsco()` await `connection()`, the root layout streams its `DataProvider` under `<Suspense>`, `lib/db-read.mjs` throws if called while `NEXT_PHASE=phase-production-build`, and inside `"use cache"` scopes use `cachedSeed()` after the route has awaited `getSeed()`. So `next build` (Vercel) needs no database credentials; the deployed app needs `TIGER_DATABASE_URL` + `TIGER_DATABASE_PASSWORD` at runtime. Connection: `lib/db-config.mjs` (Supabase via the IPv4 session pooler as `postgres.<ref>`, TLS always verified against the embedded Supabase root CA) and `lib/db.ts` (pg pool, server-only). Every table has row-level security with no policies, so the publishable key reads nothing; `/api/db/health` reports live row counts.

- `app/` is split into **three separate role views**, company, job seeker and organiser, not a step flow. The **organiser** (the City of Espoo event team) is the **broker**, and every pair follows one **recruitment pipeline** (`lib/pipeline.ts`, `stageOf` → stage, step, whose move): (1) applied or matched: the candidate asks to meet (Explore roles) or the company asks (Find candidates), both counting as their yes; (2) Espoo assessment: the organiser invites the candidate to an Espoo interview or passes, with a reason (`decisions`, approved = invited); (3) Espoo interview: the candidate accepts and books a slot at the Espoo desk (`screening`, `screeningAvailability`), then the organiser records passed / not passed with a reason (logged as `passed` / `not-passed`); (4) only after a pass does the company see the candidate's profile and contact details (`visibleTo`) and decide whether to interview (`optIns.company`); (5) the candidate says yes too and either side books a company interview after the Espoo one (`slots`, `slotAvailability` blocks clashes and earlier times), then both give feedback; (6) the company offers the job or not and the candidate accepts or declines (`offers`). Passing or undoing a decision clears everything after it. Nobody is told why someone said no. `/` is a role picker; `lib/roles.ts` lists each role's pages and `roleOf(pathname)` drives the header (role tabs + the current role's page nav). Company: `/company`, `/meetings/company` (labelled "Candidates from Espoo"), `/company/agenda`. Talent: `/talent`, `/talent/explore`, `/meetings/talent` ("Applications"), `/talent/agenda`. Organiser: `/organiser`, `/organiser/insights` (`/company/candidates` and `/company/insights` redirect there). `/responsible` belongs to no role (linked from the home page and footer). `/meetings` redirects to `/`. Company and talent each have one current identity (`lib/identity.ts`, `components/identity.tsx`: `useIdentity(side)` + a "Signed in as (demo)" switch, stored as `actingAs` in the demo state); meetings and agenda show **only that identity's own pairs**, never anyone else's. The switch lists candidates by name and id with "n to answer" counts and suggests other participants with pending steps; organiser toasts and the Pipeline tab open the right identity's view (`useViewAs`), and a `?pair=` link for someone else offers a switch. The organiser has no identity switch: it is one event team and sees every need. Each main page shows a hideable three-step “How this page works” strip (`components/page-guide.tsx`). UI copy is written for non-technical users: say “skill match”, “shown / stated”, “AI”, “EU skills list” and “people at this event” rather than overlap, evidenced / self-reported, Gemini, ESCO or pool (technical terms stay on `/responsible` and in tooltips). Routes: `/company` (editable need card → human approval, with live pool count and a mock reminder timeline; the clarifying intake chat is a popup opened from the round button in the bottom-right corner), the company's suitable-candidate list has "Ask the organiser to introduce" per person (sets the company's opt-in), `/organiser` (`components/organiser-review.tsx`: every company's needs with suitable candidates, skill match, evidence and synthetic name + contact details; introduce / not now / edit / undo with required reasons, logged as "Organiser (demo)"; introducing sets **no** opt-in; "Candidate asked to meet" / "Company asked for an introduction" badges never change the score; a "Pipeline" tab lists every pair from request to offer (six-step progress, Espoo interview time, both answers, interview, offer, whose move, record Espoo result); a "By company need / By candidate" switch: by candidate, pick a person and see every company ranked for them (`companiesFor` in `lib/explore.ts`: best role first, then number of strong fits; `components/company-ranking.tsx`) with introduce / not now per role, reached from each need-view card via "Other company…"; the **Espoo Esbo assistant** chat popup on every organiser page (`app/organiser/layout.tsx`, `components/organiser-assistant.tsx`, `app/api/organiser/assistant`, logic in `lib/organiser-assistant.ts`): it answers from an aggregate `eventSnapshot` (counts per company need, introductions, schedule, fairness, feedback; no candidate ids, names or skills), re-validated server-side by `sanitizeSnapshot`, links only to an allowlist of pages and never decides; rules fallback (`rulesReply`) without a key, offline or on error; the append-only decisions log with CSV export; logic in `lib/oversight.ts`; nobody is auto-rejected, people below the guide stay listed), `/organiser/insights` (`components/event-insights.tsx`: charts and headline numbers from `lib/dashboard.ts`, drawn with `components/charts.tsx`; aggregates only, each chart has a table view), `/talent` (skills translator → skill picker → four scenario answers → reviewable evidence map, privacy check and skill card; the sticky side card is "Companies that suit you best" (`components/companies-for-you.tsx`, `app/api/talent/companies`, logic in `lib/role-rank.ts`): every role scored by the skills-only rules, then an AI fit rate per role from Gemini under labels R1…Rn (only the person's own skills and evidence plus the public role cards), companies ranked by their best role, highest first, with job title, fit and skill match; rules fallback; the anonymised "What companies see" preview folds away below it), `/talent/explore` (`components/explore-roles.tsx`, logic in `lib/explore.ts`: every role ranked by the same skills-only match, a "show proof" boost for stated skills, the missing skills that would open the most roles, a "Companies that match your profile" ranking (same `companiesFor` + `CompanyRanking`), and "Ask to meet", which sets the candidate's opt-in before any introduction; the organiser sees a "Candidate asked to meet" badge, which never changes the score), `/meetings/company` and `/meetings/talent` are separate views of the same `components/meetings.tsx` (`side` prop, selected pair in `?pair=`) with a six-step stepper (`components/pipeline-steps.tsx`): the candidate answers Espoo's invitation, books the Espoo interview, sees the result, answers the company and the offer; Pages are thin Server Components that render a client component from `components/`.
- Data lives in the database: the `esco_*` tables are the ESCO subset (skills with real URIs, synonyms and adjacency; occupations with multilingual titles), refreshed in place via `yarn esco:refresh`; the seed tables hold the synthetic personas (5 companies / 7 needs, 26 talent profiles varied by origin, language, education and career path). Tests run offline on a snapshot in `tests/fixtures/` (loaded into the registries by `tests/setup.ts`; refresh with `yarn db:dump tests/fixtures`); the app never reads it. `lib/seed.ts` validates and loads the seeds (re-exported from `lib/data.ts` with event constants); `lib/esco.ts` has the lookup helpers (`searchSkills`, `relatedSkills`, `searchOccupations`), keyword extraction and title translator, and `lib/match.ts` the transparent rule-based matching (`explainMatch` returns a per-skill points `breakdown`; inputs are typed `MatchNeed`/`MatchTalent` so only skills and evidence can be read) and bias audit, and `lib/match-explain.ts` builds the "why this match" input (scoring output only) for `app/api/match/explain` and its template fallback. **Matching must use skills only**; `Talent.audit` is for aggregate fairness checks only, and `tests/match.test.ts` fails if scoring reads or depends on any protected field. `lib/store.tsx` is the `DemoProvider` / `useDemo()` state.
- **Live ESCO API** (`lib/esco-api.ts`, server-only): multilingual search (en, fi, sv, de, fr, es, pt, pl, et, uk queried in parallel, merged by URI, fuzzy junk dropped by `relevance`) and occupation details with essential/optional skills, each `"use cache"` + `cacheLife("days")`. Routes: `app/api/esco/search?q=&type=skill|occupation` and `app/api/esco/occupation?uri=`. The talent translator adds the official ESCO occupation (`esco` on the translate response); the need card's skill search adds live ESCO skills. Live concepts link to the cached subset by exact URI, else by keyword ("close"); concepts outside the subset are shown but can't be added, because **matching still runs only on the subset in the database**. Only the typed text and public URIs are sent to ESCO.
- **Scraper** (`yarn scrape [source…] [--limit N] [--no-details] [--since YYYY-MM-DD] [--list]`, `scripts/scrape/`): writes public recruitment data to `data/scraped/<source>.json` plus `_manifest.json`. Sources: The Hub FI jobs, Espoo and Helsinki Linked Events (recruitment terms), Suomi.fi PTV services for Espoo, Work in Finland, Business Espoo, OPH skills anticipation, Tavata and Brella (reference). It honours robots.txt, makes one request per second per host and stores no contact fields. Duunitori (robots.txt blocks all crawlers) and Job Market Finland (registration-only KEHA API) are listed as skipped, not scraped. `data/scraped/` is gitignored real third-party data for research only; the demo runs on the synthetic seeds in the database.
- **Feedback loop**: after a meeting each side answers a structured form (held?, meeting worth the time 1–5, card accuracy 1–5, next step, optional idea). `lib/impact.ts` turns it into the Impact section on the organiser Insights page (meetings held, no-shows, follow-ups needing interest from both, interviews, satisfaction per side, skill-card / need-card accuracy, anonymised ideas). Ratings are about the meeting and the cards, never the person.
- UI is **shadcn/ui** (`components.json`, style `base-nova`, built on **Base UI**, not Radix). Add components with `npx shadcn@latest add <name>`. Base UI uses `render={<Link href="…" />}` (plus `nativeButton={false}` on `Button`) instead of `asChild`. `cn` comes from the `cn` package (shadcn's own), re-exported from `@/lib/utils`.

Constraints from the brief that should shape product and technical decisions:

- Goal: help companies and job seekers find relevant matches before, during, and after Espoo's recruitment and matchmaking events (online, in person, or hybrid). Focus on "more signal, less noise", given that CVs and screening are increasingly generated or processed by AI.
- **No automated profiling or automated decisions about individuals without a human in the loop.** Matching may suggest; humans decide.
- **Synthetic data only.** Minimise personal data processing, and be ready to explain how privacy and EU AI Act compliance would work in a real deployment.
- Avoid bias based on nationality, language, education, or career path. Explainable or transparent matching helps here.
- Useful open resources: the ESCO skills/occupations taxonomy, Work in Finland / Job Market Finland, and Duunitori.
- Judging weights: Impact & Relevance 45%, Innovation & UX 35%, Responsible & Feasible Execution 20%. UX polish and a clear demo flow carry a lot of weight.

## Commands

The package manager is **Yarn 1** (`packageManager: yarn@1.22.22`, `yarn.lock`). Don't use npm or pnpm, so the lockfile doesn't drift.

```bash
yarn install
yarn dev      # next dev (Turbopack), http://localhost:3000
yarn build    # next build: production build, also type-checks
yarn start    # serve the production build
yarn lint     # eslint (flat config, eslint-config-next core-web-vitals + typescript + prettier)
yarn format   # prettier --write . (with prettier-plugin-tailwindcss)
yarn test     # vitest run (scoring rules, protected-attribute and privacy tests)
yarn scrape   # scrape public recruitment data into data/scraped/ (gitignored); --list for sources
yarn db:migrate  # create/upgrade tables only (--from <dir> loads a snapshot, --scraped loads data/scraped)
yarn db:dump     # snapshot the database to db/snapshot/ (or a given dir)
yarn db:sql --from <dir>  # write a snapshot load to db/migrate.sql instead (--split <KB> for SQL editors)
```

**Releases and deploys**: don't bump `version` in `package.json` by hand. On every push to `main`, `.github/workflows/version.yml` bumps it from the conventional commits since the last release (`feat` → minor, `!`/`BREAKING CHANGE` → major, minor while < 1.0, else patch; logic in `scripts/release/bump.mjs`), then pushes a `chore(release): vX.Y.Z` commit and tag. `vercel.json`'s `ignoreCommand` (`scripts/release/vercel-ignore.mjs`) skips production builds for every other `main` commit, so each change deploys once. Pull after pushing, since CI adds a commit. A Husky pre-commit hook runs lint-staged (`eslint --fix` + `prettier --write` on staged files). Tests use **Vitest** (`vitest.config.mts`, `@/` alias, files in `tests/`): run `yarn test` (or `yarn test:watch`). There is no `typecheck` script; run `yarn tsc --noEmit`.

## Non-default Next.js config (`next.config.ts`)

These flags change how pages have to be written:

- **`cacheComponents: true`**: the Cache Components model. Data is **dynamic by default**, and caching is opt-in with the `"use cache"` directive, plus `cacheLife` / `cacheTag`. An uncached async read, or a runtime API (`cookies()`, `headers()`, `searchParams`, `params`), must sit inside a `<Suspense>` boundary. Otherwise the dev overlay reports a "blocking-route" insight. The old route-segment configs (`export const dynamic`, `revalidate`, and so on) don't apply. See `docs/01-app/01-getting-started/08-caching.md`.
- **`partialPrefetching: true`**: `<Link>` prefetches only the route's static "App Shell". URL-dependent data (`params`, `searchParams`) should be read inside `<Suspense>`. Use `<Link prefetch={true}>` only when the URL-specific content really must be prefetched. See `docs/01-app/02-guides/adopting-partial-prefetching.md`.
- **`experimental.agentFeedback: true`**: `next dev` rewrites the managed block in `AGENTS.md` and restores it if removed. Commit `AGENTS.md` changes along with your work instead of reverting them.

## Conventions in the scaffold

- Layouts and pages use the global, route-typed helpers `LayoutProps<"/route">` / `PageProps<"/route">`, which Next generates into `.next/types`. No import is needed.
- Components are Server Components by default. Add `"use client"` only for interactive leaves.
- Dark mode uses `next-themes` (`.dark` class, system default) with the shadcn CSS variables in `globals.css`. Brand and semantic tokens (`--evidence`, `--transfer`, `--gap`) are defined there too.
