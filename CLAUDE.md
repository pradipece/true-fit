This file guides Claude Code (claude.ai/code) when working in this repository.

## Project status and purpose

`true-fit` is a hackathon project for the **Junction "Rethinking Recruitment" challenge by the City of Espoo**. The brief is in `espoo-challenge.pdf` at the repo root. It is untracked; on macOS, extract its text with PDFKit via `osascript -l JavaScript` if `pdftotext` isn't installed.

The MVP UI is a **front-end demo with a few API routes for the LLM steps**, all using **Google Gemini** through `@google/genai` (`lib/ai.ts`, default model `gemini-3.5-flash-lite`, override with `GEMINI_MODEL`; key in `GEMINI_API_KEY`). `app/api/intake` runs the company intake chat (its suggested answers are written by Gemini in the user's voice and tailored to the conversation, then cleaned by `cleanQuickReplies`), `app/api/intake/starters` writes the opening suggestions from aggregate pool counts (cached hourly, fixed fallback); `app/api/intake/transcribe` turns a mic recording from the chat (up to 60 s, `components/voice-input.tsx`) into text with Gemini (`transcribeAudio` in `lib/ai.ts`); the transcript fills the chat box for the user to check, it is never sent automatically, and the audio is not stored; `app/api/intake/live` starts a **live voice conversation** (Gemini Live API, model `gemini-3.8-live`, override with `GEMINI_LIVE_MODEL`): it returns a single-use ephemeral token with the model, system prompt (card + aggregate pool counts) and the `update_need_card` tool locked in, so the key never reaches the browser; `components/use-live-intake.ts` streams 16 kHz mic PCM, plays 24 kHz replies, shows both transcripts in the chat and answers each tool call with `cardPoolCheck` counts only (`lib/intake-live.ts`); `app/api/match/rank` gives an optional **AI fit rate** (0–100 plus a one-line reason) for already-matched candidates: Gemini sees only the scoring output and evidence quotes under labels C1…Cn, never ids or names, the output is re-validated (`lib/match-rank.ts`, rules fallback), and the UI (`components/ai-rank.tsx`, "Order by: Skill match / AI fit rate" on Find candidates and Candidates) keeps the skill match beside it and never hides anyone; `app/api/talent/translate` (job title or career path → ESCO skills + Finnish job-ad vocabulary) `app/api/talent/starters` (writing ideas and half-sentence starters tailored to the person's skills and background, never full answers) `app/api/talent/evidence` (answers → ESCO skills with verbatim supporting quotes, plus a privacy check) and `app/api/talent/cv` (CV import: LinkedIn "Save to PDF" export or any ATS-style CV: text-based PDF via `unpdf`, Word .docx via `fflate`, plain or pasted text; basic mode knows common English/Finnish/Swedish CV headings and date formats → latest title, anonymised career summary, quote-backed skills and languages; contact details are stripped before Gemini, the file is never stored, logic and rules fallback in `lib/cv-import.ts`, UI in `components/cv-import.tsx`) power the talent card. Skills from a CV only ever count as _stated_; the scenario answers are what can show them. On the need card, working language, way of working and contract type are **free text** (presets are one-tap shortcuts) and Gemini may set or change any card field to any wording; only skills stay limited to the cached ESCO ids. `lib/need-terms.ts` reads that text back for pool counts, the native-speaker warning and the online-room check; seed needs still use the presets (the `db/schema.sql` CHECKs only cover seeds). The intake's quick replies and their hints ("6 in the pool", "+2 relevant") come from aggregate pool counts in `lib/intake.ts`; Gemini gets only those counts, never individuals. Each Gemini call is capped at 15 s, and after an overload or timeout the routes skip Gemini for 60 s. Responses use JSON-schema output constrained to the cached ESCO ids and are re-validated server-side (quotes must appear verbatim in the answer). **The company intake chat requires Gemini and an internet connection, with no fallback**: without a key or on an API error `app/api/intake` returns `{ error }` (503/502) and the chat shows the error with a retry; offline, input is disabled (the need card stays editable by hand). The intake rules engine (`rulesTurn` in `lib/intake.ts`) is no longer wired to the chat; its pool-aware helpers still drive the quick-reply hints. The talent and match-explanation routes keep their deterministic fallbacks (`lib/talent-ai.ts`, `lib/match-explain.ts`): without a key, on any API error, or with `AI_MODE=rules`, they answer from rules. Routes only see the sender's own text, never other people's data. All data is synthetic, and demo state lives in a client context persisted to `localStorage`.

**Tiger Data** (Timescale Cloud, `TIGER_DATABASE_URL`) is the preferred database: when set, `dbConfig()` in `lib/db-config.mjs` picks it over Supabase for both the app and `yarn db:migrate` (TLS verified against Node's public CA store, `sslmode` dropped; `TIGER_DATABASE_CA` pins a CA). `yarn db:csv` writes one CSV per table plus `import.sql` (`\copy` in foreign-key order) to `db/csv/` for Tiger's CSV import. Everything below about the schema, `getSeed()` and the JSON fallback applies to either database. **Supabase** holds the seed data (`db/schema.sql`, loaded by `yarn db:migrate` from `data/`, which stays the source of truth; the migration replaces table contents on every run). The server reads companies, needs and talent through `getSeed()` in `lib/seed-db.ts` (`"use cache"`, validated by `loadSeed`) and passes them from the root layout to `DemoProvider`; the intake, schedule and Responsible routes use it too. Without Supabase configured, or if it is unreachable, `getSeed()` falls back to the JSON seeds. The ESCO subset is also in the database but the app still reads it from `data/esco` (it is used synchronously in the browser). Connection: `lib/db-config.mjs` (IPv4 session pooler as `postgres.<ref>`, TLS always verified against the embedded Supabase root CA) and `lib/db.ts` (pg pool, server-only). Every table has row-level security with no policies, so the publishable key reads nothing; `/api/db/health` reports live row counts.

- `app/` is split into **two separate role views**, company and job seeker, not a step flow. There is **no organiser role**: companies decide whom to invite, candidates decide whom to meet. `/` is a role picker; `lib/roles.ts` lists each role's pages and `roleOf(pathname)` drives the header (role tabs + the current role's page nav). Company: `/company`, `/company/candidates`, `/meetings/company`, `/company/agenda`, `/company/insights`. Talent: `/talent`, `/talent/explore`, `/meetings/talent`, `/talent/agenda`. `/responsible` belongs to no role (linked from the home page and footer). `/meetings` redirects to `/`. Each side has one current identity (`lib/identity.ts`, `components/identity.tsx`: `useIdentity(side)` + a "Signed in as (demo)" switch, stored as `actingAs` in the demo state); meetings, agenda and candidate review show **only that identity's own pairs**, never anyone else's. Each main page shows a hideable three-step “How this page works” strip (`components/page-guide.tsx`). UI copy is written for non-technical users: say “skill match”, “shown / stated”, “AI”, “EU skills list” and “people at this event” rather than overlap, evidenced / self-reported, Gemini, ESCO or pool (technical terms stay on `/responsible` and in tooltips). Routes: `/company` (editable need card → human approval, with live pool count and a mock reminder timeline; the clarifying intake chat is a popup opened from the round button in the bottom-right corner), `/company/candidates` (`components/candidate-review.tsx`: suitable candidates for the signed-in company's needs with skill match, evidence and synthetic name + contact details; invite / not now / edit / undo with required reasons, inviting also sets the company's opt-in; the company's own append-only decisions log with CSV export; logic in `lib/oversight.ts`; nobody is auto-rejected, people below the guide stay listed), `/company/insights` (`components/event-insights.tsx`: charts and headline numbers from `lib/dashboard.ts`, drawn with `components/charts.tsx`; aggregates only, each chart has a table view), `/talent` (skills translator → skill picker → four scenario answers plus optional voice note / work-sample file → reviewable evidence map, privacy check and skill card), `/talent/explore` (`components/explore-roles.tsx`, logic in `lib/explore.ts`: every role ranked by the same skills-only match, a "show proof" boost for stated skills, the missing skills that would open the most roles, and "Ask to meet", which sets the candidate's opt-in before any invite; the company sees an "Asked to meet you" badge, which never changes the score), `/meetings/company` and `/meetings/talent` are separate views of the same `components/meetings.tsx` (`side` prop, selected pair in `?pair=`), each showing only its own pairs, answers and feedback form: the candidate accepts or declines an invitation → book a 10-min slot from the pre-generated schedule, clashes checked per company table and per candidate → feedback; logic in `lib/schedule.ts`; `/company/agenda` and `/talent/agenda` (`components/my-agenda.tsx`: the signed-in participant's own agenda with .ics export), `/api/schedule` (static, cached JSON of slots and rooms) and `/responsible` (who decides what per step, what the AI does / never does, bias check per nationality, language, education and career path with match rate, avg best overlap and four-fifths ratio, data inventory with what is sent where and retention, EU AI Act note with Annex III 4(a) classification and a prototype-vs-production table). Pages are thin Server Components that render a client component from `components/`.
- Data lives in JSON: `data/esco/` is the cached ESCO subset (skills with real URIs, synonyms and adjacency; occupations with multilingual titles), refreshed via `yarn esco:refresh`. `data/seed/` holds the synthetic personas (5 companies / 7 needs, 26 talent profiles varied by origin, language, education and career path). `lib/seed.ts` validates and loads the seeds (re-exported from `lib/data.ts` with event constants); `lib/esco.ts` has the lookup helpers (`searchSkills`, `relatedSkills`, `searchOccupations`), keyword extraction and title translator, and `lib/match.ts` the transparent rule-based matching (`explainMatch` returns a per-skill points `breakdown`; inputs are typed `MatchNeed`/`MatchTalent` so only skills and evidence can be read) and bias audit, and `lib/match-explain.ts` builds the "why this match" input (scoring output only) for `app/api/match/explain` and its template fallback. **Matching must use skills only**; `Talent.audit` is for aggregate fairness checks only, and `tests/match.test.ts` fails if scoring reads or depends on any protected field. `lib/store.tsx` is the `DemoProvider` / `useDemo()` state.
- **Live ESCO API** (`lib/esco-api.ts`, server-only): multilingual search (en, fi, sv, de, fr, es, pt, pl, et, uk queried in parallel, merged by URI, fuzzy junk dropped by `relevance`) and occupation details with essential/optional skills, each `"use cache"` + `cacheLife("days")`. Routes: `app/api/esco/search?q=&type=skill|occupation` and `app/api/esco/occupation?uri=`. The talent translator adds the official ESCO occupation (`esco` on the translate response); the need card's skill search adds live ESCO skills. Live concepts link to the cached subset by exact URI, else by keyword ("close"); concepts outside the subset are shown but can't be added, because **matching still runs only on the cached subset**. Only the typed text and public URIs are sent to ESCO.
- **Scraper** (`yarn scrape [source…] [--limit N] [--no-details] [--since YYYY-MM-DD] [--list]`, `scripts/scrape/`): writes public recruitment data to `data/scraped/<source>.json` plus `_manifest.json`. Sources: The Hub FI jobs, Espoo and Helsinki Linked Events (recruitment terms), Suomi.fi PTV services for Espoo, Work in Finland, Business Espoo, OPH skills anticipation, Tavata and Brella (reference). It honours robots.txt, makes one request per second per host and stores no contact fields. Duunitori (robots.txt blocks all crawlers) and Job Market Finland (registration-only KEHA API) are listed as skipped, not scraped. `data/scraped/` is gitignored real third-party data for research only; the demo keeps running on synthetic seeds.
- **Feedback loop**: after a meeting each side answers a structured form (held?, meeting worth the time 1–5, card accuracy 1–5, next step, optional idea). `lib/impact.ts` turns it into the Impact section on the company Insights page (meetings held, no-shows, follow-ups needing interest from both, interviews, satisfaction per side, skill-card / need-card accuracy, anonymised ideas). Ratings are about the meeting and the cards, never the person.
- UI is **shadcn/ui** (`components.json`, style `base-nova`, built on **Base UI**, not Radix). Add components with `npx shadcn@latest add <name>`. Base UI uses `render={<Link href="…" />}` (plus `nativeButton={false}` on `Button`) instead of `asChild`. `cn` comes from the `cn` package (shadcn's own), re-exported from `@/lib/utils`.

Constraints from the brief that should shape product and technical decisions:

- Goal: help companies and job seekers find relevant matches before, during, and after Espoo's recruitment and matchmaking events (online, in person, or hybrid). Focus on "more signal, less noise", given that CVs and screening are increasingly generated or processed by AI.
- **No automated profiling or automated decisions about individuals without a human in the loop.** Matching may suggest; humans decide.
- **Synthetic data only.** Minimise personal data processing, and be ready to explain how privacy and EU AI Act compliance would work in a real deployment.
- Avoid bias based on nationality, language, education, or career path. Explainable or transparent matching helps here.
- Useful open resources: the ESCO skills/occupations taxonomy, Work in Finland / Job Market Finland, and Duunitori.
- Judging weights: Impact & Relevance 45%, Innovation & UX 35%, Responsible & Feasible Execution 20%. UX polish and a clear demo flow carry a lot of weight.

## Commands

The package manager is **Yarn 1** (`packageManager: yarn@1.22.22`, `yarn.lock`). Don't use npm or pnpm, so the lockfile doesn't drift.

```bash
yarn install
yarn dev      # next dev (Turbopack), http://localhost:3000
yarn build    # next build: production build, also type-checks
yarn start    # serve the production build
yarn lint     # eslint (flat config, eslint-config-next core-web-vitals + typescript + prettier)
yarn format   # prettier --write . (with prettier-plugin-tailwindcss)
yarn test     # vitest run (scoring rules, protected-attribute and privacy tests)
yarn scrape   # scrape public recruitment data into data/scraped/ (gitignored); --list for sources
yarn db:migrate  # load data/ into Supabase (--no-scraped to skip scraped data)
yarn db:sql      # write the same migration to db/migrate.sql instead (--split <KB> for SQL editors)
```

**Releases and deploys**: don't bump `version` in `package.json` by hand. On every push to `main`, `.github/workflows/version.yml` bumps it from the conventional commits since the last release (`feat` → minor, `!`/`BREAKING CHANGE` → major, minor while < 1.0, else patch; logic in `scripts/release/bump.mjs`), then pushes a `chore(release): vX.Y.Z` commit and tag. `vercel.json`'s `ignoreCommand` (`scripts/release/vercel-ignore.mjs`) skips production builds for every other `main` commit, so each change deploys once. Pull after pushing, since CI adds a commit. A Husky pre-commit hook runs lint-staged (`eslint --fix` + `prettier --write` on staged files). Tests use **Vitest** (`vitest.config.mts`, `@/` alias, files in `tests/`): run `yarn test` (or `yarn test:watch`). There is no `typecheck` script; run `yarn tsc --noEmit`.

## Stack and versions

These are newer than most training data. Check `node_modules/next/dist/docs/` before relying on memory (see AGENTS.md).

- **Next.js 16.4** with the App Router only (`app/`, no `pages/`, no `src/`). **React 19.3**, **TypeScript 5** in strict mode.
- **Tailwind CSS v4**, CSS-first. There is no `tailwind.config.*` and no PostCSS config. Tailwind runs through the `@tailwindcss/turbopack` loader, set up under `turbopack.rules` in `next.config.ts`. `app/globals.css` uses `@import "tailwindcss"`, and theme tokens are defined in `@theme inline`. Add design tokens there, not in a JS config.
- Fonts: Geist and Geist Mono via `next/font/google`, exposed as `--font-geist-sans` / `--font-geist-mono` and mapped to Tailwind's `font-sans` / `font-mono`.
- Path alias: `@/*` resolves to the repo root (for example `@/app/...`). If you add `lib/` or `components/` at the root, import them as `@/lib/...`.

## Non-default Next.js config (`next.config.ts`)

These flags change how pages have to be written:

- **`cacheComponents: true`**: the Cache Components model. Data is **dynamic by default**, and caching is opt-in with the `"use cache"` directive, plus `cacheLife` / `cacheTag`. An uncached async read, or a runtime API (`cookies()`, `headers()`, `searchParams`, `params`), must sit inside a `<Suspense>` boundary. Otherwise the dev overlay reports a "blocking-route" insight. The old route-segment configs (`export const dynamic`, `revalidate`, and so on) don't apply. See `docs/01-app/01-getting-started/08-caching.md`.
- **`partialPrefetching: true`**: `<Link>` prefetches only the route's static "App Shell". URL-dependent data (`params`, `searchParams`) should be read inside `<Suspense>`. Use `<Link prefetch={true}>` only when the URL-specific content really must be prefetched. See `docs/01-app/02-guides/adopting-partial-prefetching.md`.
- **`experimental.agentFeedback: true`**: `next dev` rewrites the managed block in `AGENTS.md` and restores it if removed. Commit `AGENTS.md` changes along with your work instead of reverting them.

## Conventions in the scaffold

- Layouts and pages use the global, route-typed helpers `LayoutProps<"/route">` / `PageProps<"/route">`, which Next generates into `.next/types`. No import is needed.
- Components are Server Components by default. Add `"use client"` only for interactive leaves.
- Dark mode uses `next-themes` (`.dark` class, system default) with the shadcn CSS variables in `globals.css`. Brand and semantic tokens (`--evidence`, `--transfer`, `--gap`) are defined there too.
